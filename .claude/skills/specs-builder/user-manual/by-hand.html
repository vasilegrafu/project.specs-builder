Part 2: Working with Claude

Under the hood: by hand

This page is optional. Claude normally runs these commands for you. If you're curious, or you're a developer, doing it once by hand shows you what happens underneath.

You type these in a terminal. Every command below is tried automatically by the skill's own tests, so they work exactly as written.

Create the specification, then go into its folder:

python .claude/skills/specs-builder/scripts/new_spec.py invoices --name "Invoices" --kind application --summary "Customers take an invoice out of the portal as a PDF, so that they stop writing to support for it."
cd invoices

Check it, and add the goal that everything else serves:

python app/spec.py check
python app/spec.py do add goal "Fewer letters to support"

A requirement must have at least one acceptance criterion, so the two go in together, as one change. Put these two lines in a file called first.txt. $1 means "what the first line made":

add requirement "Download an invoice" priority=must statement="When a customer selects Download on an invoice, the portal shall give them its PDF." serves=G1
add-row $1 says="Given a paid invoice, when Download is selected, then its PDF is saved."

Then apply it, add an open question, and read the result:

python app/spec.py do --file first.txt
python app/spec.py do add question "How long invoices are kept" question="How long are invoices kept?" why="It decides what the list shows" answers="the product side" about=R1
python app/spec.py node R1
python app/spec.py open  # exits 1: something is open

open lists everything not settled, and Q1 is there. Before you change something, ask what it would affect:

python app/spec.py impact R1

It says Q1 would need reading again. Answer the question. An answer becomes a decision, with its reason:

python app/spec.py do answer Q1 "Seven years." because="The law where the shop sells"

Now change the requirement. --because goes in the log:

python app/spec.py do set R1 priority should --because "Support can wait a release"
python app/spec.py stale  # exits 1: something is stale

The decision D1 stands on R1, and R1 has just changed, so D1 is now stale: someone must read it again against the change. stale shows a short print beside each stale node, of everything it stands on as it is now. Once you have read it, confirm it with that print; a confirmation without one, or with an older one, is refused, so nothing is confirmed unread:

python app/spec.py stale D1  # exits 1: D1 is stale, and the line to confirm it with is shown
python app/spec.py do confirm D1 <print>
python app/spec.py verify

verify now says the specification may be built from. See the requirement as the tests a builder will write, and export the whole thing as one file:

python app/spec.py tests R1 --gherkin
python app/spec.py export

The export is in export/invoices.html. To see it all in the application, run index.cmd on Windows, or sh index.sh on macOS and Linux.

To try a change without making it, add --dry-run to any do.
